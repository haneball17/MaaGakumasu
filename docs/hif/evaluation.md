# HIF 评价体系

本页专门整理 HIF 的“怎么评”，并说明哪些内容已经可以进入评分配置，哪些仍然只是机制说明。

## 1. 评价体系结论分层

### 高可信结论

- 选拔属性奖励可拆成 `600 / 500 / 1100`
- 本战结果按 `Round1 × 1.2 + Round2 × 1.0`（2026-08-16 修正：×1.2 疑似仅 R1 取得第 1 位时适用，数据侧 `examBattleFirstRankBonusPermil: 200` 印证；待実機验证，见 mechanics.md H1/V1）
- 星性在 HIF 中地位很高
- 属性贡献不是固定 `33/33/33`

### 中可信结论

- 星性更适合视为乘区或核心资源，而不是简单附属分
- 高评价路线会显著依赖：
  - 星性
  - 记忆质量
  - 牌组厚度
  - `Interval` 预算

### 当前工程假设

- CLI 中的完成度阈值
- `SelectionSnapshot` 与 `SelectionMemoryProfile` 的字段裁剪
- 当前 `selection_evaluation / finals_evaluation / star_evaluation` 的代理定义

## 2. 前置条件与评价边界

HIF 的评价讨论不是完全脱离系统边界的。

当前需要明确的前提包括：

- HIF 本身有参与门槛
  - 当前高可信门槛是 `親愛度27`
- 后续 STEP4 / `一番星` 相关成长与 `親愛度37`、`S4+` 等目标有关
- 当前主线讨论的 HIF，会默认纳入剧本内提供的 `カスタムPアイテム`
- 但并不默认建立在：
  - `チャレンジPアイテム`
  - `レジェンドカード`
  - 其他更后期、额外成长系统
  之上

因此后续开发里，“HIF 的评价体系”应该理解成：

- 先讨论 HIF 本身的结构与驱动项
- 再考虑额外成长系统如何叠加

这也是为什么当前 simulator 的报表更适合被看作：

- HIF 主体机制的开发抽象
- 而不是所有外围系统叠满后的终局公式

## 3. 选拔属性奖励结构

当前最关键的可确认结论：

- 固定属性总量：`600`
- 浮动属性总量：`500`
- 选拔属性总量：`1100`
- HIF 剧本参数上限当前按攻略站资料记为 `3000`

折算占比：

- 固定部分：`600 / 1100 ≈ 54.5%`
- 浮动部分：`500 / 1100 ≈ 45.5%`

### 选拔结构的开发含义

这意味着选拔阶段至少有两类目标：

1. **过试验 / 拿到足够分数**
2. **让浮动部分尽量分配到需要的属性**

所以后续评分器里不能只看“过不过”，还要看：

- 主属性是否吃到更多收益
- 副属性是否维持在安全区

## 4. 本战权重结构

当前可确认：

- `Round1 × 1.2`（疑似仅 R1 第 1 位时，待実機验证）
- `Round2 × 1.0`

折算占比：

- `Round1 ≈ 54.5%`
- `Round2 ≈ 45.5%`

### 属性适配的开发含义

后续本战目标不能只写一个统一总分字段，至少要区分：

- `Round1` 稳定性与分数上限
- `Interval` 预算
- `Round2` 冲分能力

在当前 CLI 报表中，这部分已经抽象成：

- `finals_evaluation.round1_ratio`
- `finals_evaluation.round2_ratio`

## 5. 星性的地位

从当前资料看，星性更适合被理解成：

- HIF 的主资源
- 试验 / 本战表现的重要驱动项
- 高评价路线的关键变量

不建议把它简单当作：

- “总评价的一个普通加分项”

更合理的开发抽象是：

- 星性 = 高优先级评分项
- 星性 = 路线规划和 P 道具决策的重要目标
- 星性 = 与 `HIFボーナス`、`カスタムPアイテム`、拿卡次数、选拔 / 本战表现高度耦合的主资源

### 当前已进入配置的星性相关字段

当前 `HIFEvaluationConfig` 已可稳定承载：

- `selection_star_reward_cap`
- `selection_star_reward_cap_with_bonus`
- `public_lesson_star_total`
- `hif_wappen_star_cap`

### 当前仍不应写死的部分

- 星性对试验 / 本战分数的精确倍率关系
- 星性在最终高评价中的精确权重

### 星性与 `HIFボーナス` 的关系

当前资料至少支持下面的开发理解：

- `HIFボーナス` 会影响资源获取节奏
- `カスタムPアイテム` 会改变路线中的阶段收益结构
- 资源节奏会反过来影响：
  - 能否多拿卡
  - 能否更容易形成 HIF 专用 P 道具协同
  - 能否更稳定拉起星性

所以从工程抽象看：

- 星性是结果层核心资源
- `HIFボーナス` 更接近前置成长层 / 外部补正层
- `カスタムPアイテム` 更接近剧本内正式选择层

二者不应混成一个字段，但在路线价值评估里必须联动考虑

## 6. 属性适配

当前不能把 HIF 理解成固定属性比例题。

更准确的结论是：

- 属性收益受当场审查倍率影响
- 不同场次的有效属性结构会变
- 某一属性过低可能产生惩罚

### 开发含义

后续评分器应至少具备：

- 动态属性权重输入
- 主副属性目标
- 低属性风险提示

当前阶段适合：

- 先把这部分写成说明字段
- 不直接塞进首版主评分器

## 7. 低属性惩罚

当前可以确认：

- 低属性惩罚是需要考虑的机制

当前不能确认：

- 精确公式
- 全部适用条件
- 不同阶段的一致性

### 当前处理建议

本轮只在文档与评价配置里保留说明，不把它硬编码成精确数值逻辑。

## 8. 当前开发抽象建议

### 可以直接进入评分配置的部分

- 选拔属性结构
- 本战权重结构
- 星性来源结构
- 选拔 / 本战的目标字段
- `HIFボーナス` 的“影响方向”说明字段

### 先做说明字段，不直接进入主评分器的部分

- 低属性惩罚
- 动态属性倍率
- 最终高评价总公式
- `3000` 上限下具体路线收益差异这类社区经验

## 9. 与当前 CLI 报表的关系

当前 CLI 里的这些字段，正是评价体系的工程映射：

- `selection_evaluation`
  - 选拔结构与完成度
- `finals_evaluation`
  - 本战结构与完成度
- `star_evaluation`
  - 星性水平与来源对照
- `overall_assessment`
  - 当前样本的强弱项总结

## 10. 一句话总结

HIF 的评价体系，不是“一个固定百分比公式”，而是：

> 选拔属性分配结构 + 本战两轮权重 + 星性核心资源 + 动态属性适配 + 低属性风险

这也是后续 `HIFEvaluationConfig` 应该持续承载的方向。
