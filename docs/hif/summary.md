# HIF 资料总复盘

本页是当前 HIF 资料的统一结论页，服务后续开发。

如果只看一篇，请先看这篇；如果要追出处，再看：

- [`research.md`](research.md)
- [`evaluation.md`](evaluation.md)
- [`randomness.md`](randomness.md)

## 1. HIF 剧本结构

当前可确认的 HIF 主结构是：

- **选拔试验模式**
  - 共 20 日
  - 期间会经历 3 次试验
- **本战模式**
  - 共 7 日
  - 关键阶段是：
    - `Round1`
    - `Interval`
    - `Round2`

这一结构属于攻略站共识，且与当前工程抽象完全一致。

## 2. HIF 前置条件与系统边界

### 2.1 当前可确认的 HIF 参与条件

当前高可信前置条件包括：

- HIF 挑战入口要求角色 `親愛度27`

这一点是当前剧本解锁的最低前置条件，属于直接影响自动化入口判断的事实。

### 2.2 与后续 STEP4 / 一番星相关的边界

当前还存在一个容易混淆但需要分开的条件：

- `親愛度37`

它不是 HIF 的基础参与条件，而是和后续 `プリマステラ化 / 一番星` 解锁相关。  
根据现有攻略资料，`親愛度37` 的到达与 HIF 本战获胜有关。

### 2.3 当前系统限制

当前文档里需要单独记住的系统边界有：

- HIF 的讨论不是无限制环境
- HIF 自带的 `カスタムPアイテム` 属于当前剧本内机制，应视为后续模拟与决策输入的一部分
- `チャレンジPアイテム` 不是 HIF 当前主线前提
- `レジェンドカード` 也不应被当作 HIF 当前通用前提
- 攻略站资料已明确把 HIF 的参数上限写为 `3000`
  - 这可以作为当前文档里的**攻略站共识**记录
- 但围绕“上限抬高后对路线价值的具体影响有多大”的说法，仍有不少社区经验成分
  - 这一层暂不写成精确机制公式

这几条会直接影响后续模拟器解释：

- 当前样本默认不是“无限制终局资源环境”
- 文档与 simulator 应默认纳入 HIF 自带的 `カスタムPアイテム` 机制
- 但不能默认玩家已完成 `チャレンジPアイテム`、`レジェンドカード` 等额外成长系统

## 3. 当前最重要的机制结论

### 3.1 选拔不是单纯堆分，而是“固定属性 + 可分配属性”

当前最关键的已知结论是：

- 选拔总属性奖励可拆成：
  - 固定部分：`600`
  - 浮动部分：`500`
  - 总计：`1100`

也就是说，选拔阶段不是“分数越高总属性越无限增长”，而是：

- 一部分属性是固定给的
- 另一部分属性会根据试验表现分配到不同方向

这对路线决策很关键，因为它决定了：

- 选拔不只是要过关
- 还要让主副属性分配尽量贴近目标 build

### 3.2 本战不是两轮平权

当前可确认：

- `Round1 × 1.2`
- `Round2 × 1.0`

折算后：

- `Round1` 约占 `54.5%`
- `Round2` 约占 `45.5%`

这意味着：

- `Round1` 不能只求稳过
- 它对最终本战结果的影响略高于 `Round2`

### 3.3 星性是 HIF 的核心资源

当前资料已经足够支持这个判断：

- 星性不是简单附属分
- 更接近 HIF 的核心资源或乘区
- 它和试验、本战表现高度相关

所以后续开发里，星性不应只作为一个普通数值字段，而应视为：

- 高优先级评分项
- 关键时点资源
- 高评价路线的重要驱动项

### 3.4 属性占比不是固定值

当前不能把 HIF 理解成固定 `Vo/Da/Vi = 33/33/33`。

更准确的结论是：

- 当场审查倍率会影响属性收益
- 低属性可能存在惩罚
- 因此属性决策是动态的，不是静态比例题

这点会直接影响后续的评分配置设计。

## 4. HIF 固定日程骨架

### 4.1 选拔 20 日固定骨架

当前高可信事实是：

- HIF 选拔不是完全自由排程
- 其日程骨架是固定的

按现有 Wiki 资料，选拔阶段固定结构至少包括：

- `1日`：`相談 / 差し入れ / 特別指導`
- `2日`：`公開レッスン`
- `3日`：`授業`
- `4日`：`公開レッスン`
- `5日`：`おでかけ / 相談`
- `6日`：`授業`
- `7日`：`選抜試験①`
- `8日`：`おでかけ / 差し入れ`
- `9日`：`公開レッスン`
- `10日`：`授業`
- `11日`：`公開レッスン`
- `12日`：`相談 / 特別指導`
- `13日`：`選抜試験②`
- `14日`：`おでかけ / 差し入れ`
- `15日`：`公開レッスン`
- `16日`：`おでかけ / 相談 / 差し入れ`
- `17日`：`授業`
- `18日`：`公開レッスン`
- `19日`：`相談 / 特別指導`
- `20日`：`選抜試験③`

对开发的意义是：

- 不是每天都生成同质候选池
- 候选类型应按固定日程注入
- “哪天能拿几张卡”本身就是路线价值的重要组成

### 4.2 本战 7 日固定骨架

当前高可信事实是：

- 本战也是固定结构，不是自由周计划

按现有资料：

- `1日`：`授業`
- `2日`：`公開レッスン`
- `3日`：`おでかけ / 差し入れ`
- `4日`：`授業`
- `5日`：`公開レッスン`
- `6日`：`相談`
- `当日①`：`Round1`
- `当日②`：`Interval`
- `当日③`：`Round2`

### 4.3 本战第 3 日特殊约束

这是当前文档里需要单独强调的点：

- 本战不是每天都能自由选择所有常见行动
- 第 3 日是明确的特殊节点：
  - `おでかけ`
  - `差し入れ`

这意味着对后续 simulator 来说：

- 第 3 日不能被抽象成普通“自由恢复 / 资源日”
- 它应被视为固定骨架中的单独决策位

## 5. `HIFボーナス` 与 `カスタムPアイテム` 的当前定位

当前文档应把 `HIFボーナス` 理解为：

- HIF 特有的成长层
- 会影响 P 点、咨询折扣、路线节奏与资源压力
- 属于“当前未完整接入 simulator，但不能忽略”的关键机制

同时也要把 `カスタムPアイテム` 视为 HIF 当前剧本内的正式决策对象：

- 它和 `HIFボーナス` 一样，都会直接改变路线价值判断
- 它属于 HIF 主线机制本体，不应和 `チャレンジPアイテム` 混为一类

现有攻略站资料支持：

- 一开始建议先全开
- 然后优先：
  - `選抜試験` 初期 P 点
  - `相談` 割引
  - `本戦` 初期 P 点

对开发的意义：

- `HIFボーナス` 不是普通背景系统
- `カスタムPアイテム` 也不是外围补充项，而是 HIF 当前剧本内的正式选择层
- 它们会显著改变：
  - 起始资源
  - 某些日程的价值
  - 前后期的路线重心
  - 选拔结束后本战输入的质量

当前为什么还没正式接入 simulator：

- 还没有稳定的真实参数表进入本地结构化数据
- 当前 CLI 样本更偏“无完整成长补正的可解释样本”

## 6. 当前已确认的随机要素

HIF 不是“全流程随机”，更像：

- **固定骨架**
- **局部收益波动**
- **事件触发随机**
- **奖励候选随机**
- **对战抽牌随机**

当前最值得纳入模拟器的随机项包括：

- 公开课 / 部分日程收益波动
- 支援卡事件触发
- 奖励候选池
- 对战抽牌与局内顺序

详细整理见：

- [`randomness.md`](randomness.md)

## 7. 对开发最重要的抽象

### 7.1 已经适合写进配置的内容

当前已经适合做成显式配置的有：

- `HIFEvaluationConfig`
  - 选拔属性结构
  - 本战权重结构
  - 星性来源结构
- 选拔目标字段
  - 试验准备度
  - 星性
  - 记忆质量
  - 牌组质量
- 本战目标字段
  - `Round1 / Round2`
  - `Interval` 预算
  - 本战准备度

### 7.2 目前只能作为说明或代理值的内容

当前还不适合硬写死成“真实机制”的有：

- 最终高评价总公式
- 星性对分数的精确倍率关系
- 低属性惩罚的精确幅度
- 奖励池、事件池的完整真实分布

这些目前只能：

- 写进文档说明
- 做开发代理值
- 待实机验证后再提高权重

## 8. 当前已落实到代码 / 模拟器的部分

当前仓库已经有：

- HIF 入口与主流水线骨架
- HIF `CustomAction` 骨架
- 离线 `CLI` 决策模拟器
- HIF 评价报表
- `SelectionSnapshot`
- `SelectionMemoryProfile`
- `selection_evaluation / finals_evaluation / star_evaluation`

这些说明 HIF 已经不是纯文档阶段，而是进入了：

- 文档
- 数据
- 模拟

三条线并行的状态

## 9. 当前仍未落地的部分

当前还没有真正完成的部分包括：

- HIF 实机闭环
- 真实候选池接入
- 实机奖励池接入
- 出牌模拟
- 多角色泛化
- 高评价优化阶段的可靠策略器

## 10. 当前资料空白区 / 待实机验证区

后续开发最应该优先补实机的地方：

- HIF 固定日程实际候选池
- `相談` 内部的真实选项与收益
- 本战前支援事件是否、何时触发
- 星性对试验 / 本战分数的实际影响
- 公开课收益波动的真实分布
- `HIFボーナス` 的完整本地结构化字段
- “参数上限增加初始值约 `3000`”这类社区说法的实机确认

## 11. 当前开发建议

如果从开发优先级看，建议顺序是：

1. 先把 HIF 机制结论稳定收束到文档
2. 再把真实候选池和随机变量补进 CLI 模拟器
3. 再把 HIF 评价体系真正接回主评分器
4. 最后接回实机自动化

## 12. 一句话总结

当前 HIF 已经可以这样理解：

> 它是一个“固定骨架下，通过星性、属性分配、记忆质量和本战两轮权重来决定结果”的剧本，而不是单纯比一次总分的线性流程。
