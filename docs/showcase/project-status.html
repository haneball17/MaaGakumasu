系统分层

项目采用 MaaFramework 的 JSON pipeline 加 Python Custom recognition/action。JSON 负责识别页面、路由和可见动作顺序；Python 处理状态读取、决策与受守卫保护的设备操作。

用户入口 / 配置

assets/tasks/*.json 定义任务和选项；pipeline override 将难度、HIF 预设和策略参数注入目标节点。

assets/lang/ 管理多语言 UI。

→
MaaFramework Pipeline

assets/resource/base/pipeline/*.json 以识别条件驱动状态机。

通用初 / NIA 流程与 HIF 流程分开；弹窗、页面锚、跳转和安全停止在此组合。

→
Agent 动作与决策

agent/custom/ 面向现有培育/设备动作。

agent/hif/decisions 实机读状态、评分与操作；algorithms 和 roundsim 是离线逻辑。

结构化资料

assets/data/ 保存卡牌、效果、饮料、角色及 HIF 决策参数。

HIF 主数据由同步脚本生成，避免手工编辑衍生表。

⇄
设备 / 回放

MuMu + ADB 是主要实机环境；pipeline/replay suite 提供截图回放入口。

操作记录写入 debug 决策日志、截图和 ops JSONL；调试产物不入库。

→
工具与可视化

tools/maa_dev.py、数据同步、回放、校准工具。

Round simulator 另有 FastAPI + Vue 单文件 UI，用于配置、A/B 对比和 trace 回放。

分层的实际价值

这种拆分使页面覆盖、安全边界和决策算法可单独迭代。主要风险是接口和配置跨多处：任务选项、pipeline 节点名、Custom action 参数、preset 覆盖和语言文案必须保持一致。HIF 的 OCR 文本还受 IPC 编码限制，代码侧要求用 ASCII 通配 expected 再在 Python 结果里筛选日文。

实机主链 已多次走通

明确保留的缺口

  • 探索路径尚未齐全：Interval 商店全流程、特別指導、再挑战/胜利分支、Memory 再生成/转换、日志页手牌信息等。
  • RoundSim 的角色构筑和部分机制仍是显式近似；实现计划列出 R1 终局分、R2 初始状态和卡组计数等实机校准输入缺失。
  • 适配重点集中在姫崎莉波「ガラクタロード」好调路线，不能推断多角色或多卡覆盖完成。
  • 文档列出的残余实机事项包括 P 道具入口坐标、牌堆查看器证据、灰卡阈值、P 饮料栏有瓶场景、跨天弹窗等边界。

Round 模拟器：离线能力完整，校准数据仍有限

模拟器在 agent/hif/roundsim/ 内按牌组、效果引擎、状态和策略运行回合，支持 trace、A/B、固定随机种子和 Web UI。它与实机 pipeline 分离；仓库规则明确不把未经验证的模拟结果直接接到实机决策。

实施块文档状态价值 / 限制
M1–M3完成运行骨架、部分效果、抽牌和 P item 触发；未建模效果通过 precheck 明确失败，避免静默近似。
M4：策略与 A/B完成GarakutaRinamiStrategy、贪心基线、共同随机数及 bootstrap 区间；比较结果依赖预设牌组与模型假设。
M5：实机校准框架完成，数据待补文档记录模拟总分远低于实机落点，候选原因为准备期属性快照偏低、牌组重构近似及未建模乘区。用于绝对得分预测时证据不足。
M-UIa / M-UIb完成FastAPI + Vue 离线单文件 UI，支持 trace、配置、A/B、接口 schema；UI 完成不等同于用户端功能发布。
主用途目前更可信的是策略间相对比较与假设探索；绝对得分落点的预测要等真实 Round 记录、入场属性和卡组实测数据补齐。文档计划与实现状态冲突，RoundSim 实施计划的里程碑表更接近代码现状，设计文档顶部仍标注“未开工”。
