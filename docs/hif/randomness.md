# HIF 随机要素

本页整理 HIF 中与后续模拟器实现最相关的随机项。

结论先说：

> HIF 不是全程随机剧本，而是“固定骨架 + 局部收益随机 + 事件随机 + 奖励随机 + 对战随机”。

## 1. 随机要素分层

### 高可信

- 存在固定骨架下的局部收益波动
- 支援卡事件存在触发随机性
- 对战过程存在抽牌随机性

### 中可信

- 奖励候选池会波动
- 某些公开课 / 日程收益在不同出现时点并不完全相同

### 当前工程假设

- 这些随机项在 CLI 中应如何参数化
- 分布如何近似
- 是否先按离散候选建模

## 2. 固定骨架 vs 非固定收益

### 固定骨架

当前高可信：

- HIF 的大结构固定
  - 选拔 20 日
  - 本战 7 日
  - `Round1 / Interval / Round2`

### 非固定收益

当前需要单独建模的不是“日程是否存在”，而是：

- 某些日程出现时，具体收益偏什么
- 某些阶段事件是否触发
- 奖励池给出什么候选

### 对开发的影响

后续模拟器里应把：

- **阶段骨架** 当作确定项
- **局部收益** 当作随机变量

### 当前明确的确定收益示例

有些内容容易被误判成“也许随机”，当前应明确归到确定项：

- 本战第 3 日只会出现：
  - `おでかけ`
  - `差し入れ`
- `差し入れ` 的基础收益结构是固定的：
  - `Pポイント80`
  - `Pドリンク1个`
  - `スキルカード1枚`

也就是说，后续 simulator 不能把这一步当成“像 NIA 那样额外随机 P 点”的模型
来处理

## 3. 公开课 / 日程收益波动

当前资料支持：

- 公开课、部分日程收益并不完全是固定常数
- 不同日可能更偏：
  - 属性
  - 星星
  - 其他收益

### 公开课收益波动的开发建议

CLI 中建议建模成：

- `schedule_reward_variant`

最小字段可以是：

- `reward_bias = attribute / star / balanced`
- `value_delta`

当前是否已实现：

- **未实现**

## 4. 支援卡事件触发随机

当前资料支持：

- 支援卡事件并非每次都固定同样时点出现
- 特别是本战前阶段，事件触发时点对路线决策有明显影响

### 支援事件的开发建议

CLI 中建议建模成：

- `support_event_trigger`
- `support_event_progress`
- `pending_support_events`

当前是否已实现：

- **部分实现**
  - 当前 simulator 已有 `support_event_progress`
  - 但还没有真实事件触发模型

## 5. 奖励候选池随机

当前资料支持：

- 奖励层的关键不确定性包括：
  - 拿卡候选
  - 强化候选
  - 删除候选
  - P 道具候选

这类随机性会直接影响：

- 路线价值
- 牌组质量
- 星星累积
- 后续 `SelectionMemoryProfile`

### 奖励池的开发建议

CLI 中建议建模成：

- `reward_pool_state`
- `skill_reward_candidates`
- `p_item_candidates`

当前是否已实现：

- **部分实现**
  - 当前已有静态 `skill_cards / p_items`
  - 但候选池仍是样本级，不是真实随机池

## 6. 对战抽牌 / 出牌随机

这是 HIF 中最明显、但当前还未纳入主线实现的随机层。

主要包括：

- 起手随机
- 抽牌顺序随机
- 牌堆 / 弃牌堆相关效果的随机命中

### 对战随机的开发影响

这会直接影响：

- `Round1`
- `Round2`
- 同一配置下的分数波动

### 对战随机的开发建议

当前阶段先不做精确出牌模拟，但后续应预留：

- `battle_draw_seed`
- `opening_hand_state`
- `round_score_distribution`

当前是否已实现：

- **未实现**

## 7. 当前最值得优先建模的随机项

如果只按开发优先级排，建议顺序是：

1. 奖励候选池随机
2. 支援卡事件触发
3. 公开课 / 日程收益波动
4. 对战抽牌随机

原因是：

- 前三项直接影响路线规划与评价报表
- 第四项更偏后续本战模拟阶段

## 8. 当前 CLI 应怎么理解这些随机项

目前 CLI 还不是随机模拟器，而是：

- 固定样本路线
- 固定候选集合
- 基于规则和评分的可解释模拟

所以当前状态是：

- **随机性已在文档中明确**
- **但尚未被完整参数化**

## 9. 非 NIA 式随机项澄清

当前 HIF 文档需要特别避免两个误建模：

### 9.1 不要把 `差し入れ` 当成 NIA 式额外随机 P 点来源

当前资料明确支持：

- `差し入れ` 没有像 NIA 那种额外随机 P 点模型

对开发的影响：

- `差し入れ` 应先按固定收益候选处理
- 随机性不应凭空加在 P 点结构上

### 9.2 不要把整个 HIF 当成自由周计划随机剧本

当前高可信事实仍然是：

- HIF 的日程骨架是固定的

对开发的影响：

- 随机性应建在“固定骨架上的局部波动”
- 而不是先随机出整周安排

## 10. 后续开发输入表

建议后续在 simulator 中逐步补这些字段：

- `schedule_reward_variant`
- `support_event_trigger`
- `pending_support_events`
- `reward_pool_state`
- `skill_reward_candidates`
- `p_item_candidates`
- `battle_draw_seed`
- `round_score_distribution`

## 11. 一句话总结

HIF 的随机点，最该先接入开发的是：

> 奖励池、支援事件、公开课收益波动

而不是一开始就把整个对战抽牌系统完全还原。
